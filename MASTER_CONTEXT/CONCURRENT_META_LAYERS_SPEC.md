# THE CONCURRENT META LAYERS SPEC — LASME ∥ MPSE ∥ SRO

**Version:** 1.0 · **Date:** 2026-08-30 · **Status:** APPROVED FOR IMPLEMENTATION
**Authority:** This document is the implementation spec. The checkpoint `v443_precision_waves_1_3_complete_async_20260830_0944` is the rollback point.

---

## §0 THE PROBLEM + THE SOLUTION

**THE PROBLEM:** The three meta gates (LASME, MPSE, SRO) run SEQUENTIALLY — each waits for the prior to complete before dispatching its hunters. Total wall clock: ~30 minutes (LASME ~10 + MPSE ~8 + SRO ~12). The sequential ordering exists because MPSE reads LASME's output and SRO reads both — but this enrichment is a NICETY, not a hard dependency. The hunters can hunt their predicates purely from the graph + the target code.

**THE SOLUTION:** Fire all three gates CONCURRENTLY via `Promise.allSettled`. Each gate writes its own prefixed section files. After all gates settle, the runner stitches the sections into the two canonical docs (doc1 meta-analysis.md, doc2 findings-report.md) in canonical layer order. Wall clock drops to ~12 minutes (the longest gate).

**THE OPERATOR'S RULING (verbatim):**
> "why dont we make the meta layers async/concurrent as well? There is no real reason it has to go LASME --> MPSE --> SRO and not just LASME/MPSE/SRO. This would make it finish in 10-15 minutes as well instead of 30"

> "the findings reports will need to be per meta layer than and once all of them are done a fresh meta agent just stitches all of them together. OR we can just keep 2→6 docs and just have a prefixed set for each meta layer that is generated by that specific meta layer. this is probably the simplest cuz then all you have to do is setup concurrency safeguards on the sequential to parallel swap between the meta layers and then everything is already setup"

**THE CHOSEN DESIGN:** The operator's preferred option — keep the 2-doc architecture, each meta layer writes its own prefixed section files, the runner stitches after allSettled.

## §1 THE CURRENT ARCHITECTURE (what exists)

### §1.1 The Sequential Gate Flow (index.ts)

```
[PRELIMINARY] ──→ LASME gate ──→ [LASME-ADJUDICATED] ──→ MPSE gate ──→ [MPSE-VERIFIED] ──→ SRO gate ──→ [FINAL]
                  (6 hunters +                          (4 hunters +                      (4 hunters +
                   1 meta agent)                        1 meta agent)                     1 meta agent)
                  ~10 min                               ~8 min                            ~12 min
```

The gates are dispatched at three separate `await runMetaLayer(...)` call sites in `src/audit-engine/index.ts`. Each gate:
1. Dispatches N hunters concurrently (already Promise.allSettled within the gate)
2. The meta agent reviews the hunters' findings
3. The runner stitches the hunters' reports into doc2 (verbatim)
4. The meta agent's analysis is appended to doc1
5. The artifact is updated to the gate's label

### §1.2 The Cross-Gate Enrichment (the dependency being removed)

- MPSE hunters read LASME's output via `memory.getGateOutput('LASME')` filtered by `filterTags`
- SRO hunters read BOTH LASME and MPSE outputs via the same mechanism
- This enrichment helps hunters focus (e.g., "LASME found a tower at r-actor.ts:94, so check the contract there")
- WITHOUT the enrichment, hunters still hunt their predicates — just without cross-gate context

### §1.3 The 2-Doc Architecture (what's preserved)

- **doc1** (`<ledgerRoot>/meta-analysis.md`) — the meta agent's judgment, appended per gate
- **doc2** (`<ledgerRoot>/findings-report.md`) — the verbatim hunter findings stitch, appended per gate
- Both are APPEND-ONLY (never rewritten)

## §2 THE CONCURRENT ARCHITECTURE (what we're building)

### §2.1 The Concurrent Gate Flow

```
[PRELIMINARY]
      ↓
  [GATES-RUNNING] ──── new label while all 3 are in flight
      ↓
  ┌────────────────┬────────────────┬────────────────┐
  │    LASME       │     MPSE       │      SRO       │  ← ALL FIRE
  │  6 hunters     │  4 hunters     │  4 hunters     │    SIMULTANEOUSLY
  │  + 1 meta      │  + 1 meta      │  + 1 meta      │
  │      ↓         │      ↓         │      ↓         │
  │  writes:       │  writes:       │  writes:       │  ← Each writes
  │  lasme-        │  mpse-         │  sro-          │    OWN files
  │  section.md    │  section.md    │  section.md    │
  │  lasme-        │  mpse-         │  sro-          │
  │  analysis.md   │  analysis.md   │  analysis.md   │
  └────────────────┴────────────────┴────────────────┘
      ↓ (Promise.allSettled)
  THE STITCH (the runner, mechanical — zero LLM tokens):
    1. Read lasme-section.md + mpse-section.md + sro-section.md
    2. Append in canonical order to doc2 (findings-report.md)
    3. Read lasme-analysis.md + mpse-analysis.md + sro-analysis.md
    4. Append in canonical order to doc1 (meta-analysis.md)
    5. Compute CORRELATIONS from all tags now in shared.db
    6. Append CORRELATIONS to doc2
      ↓
  [FINAL]
```

### §2.2 The Section Files (per-gate isolated writes)

Each gate writes TWO files to the ledger root (alongside the existing hunter dirs):

```
<ledgerRoot>/
├── R18-lasme-lexicon/findings/report.md    ← unchanged (hunter's own dir)
├── R19-lasme-actor/findings/report.md
├── ... (all 14 hunter dirs unchanged)
├── lasme-section.md                          ← NEW: the LASME meta's doc2 section
├── lasme-analysis.md                        ← NEW: the LASME meta's doc1 section
├── mpse-section.md                           ← NEW: the MPSE meta's doc2 section
├── mpse-analysis.md                         ← NEW: the MPSE meta's doc1 section
├── sro-section.md                            ← NEW: the SRO meta's doc2 section
├── sro-analysis.md                          ← NEW: the SRO meta's doc1 section
├── findings-report.md                       ← EXISTING: doc2 (stitched at the end)
├── meta-analysis.md                         ← EXISTING: doc1 (stitched at the end)
├── run-status.json                          ← EXISTING: the status file
├── notifications.jsonl                      ← EXISTING: the toast channel
└── roster.json                              ← EXISTING: the hunter roster
```

**The write isolation:** Each gate writes ONLY its own prefixed files. No gate touches doc1 or doc2 directly. The runner is the ONLY writer to doc1/doc2 (after allSettled). Zero file contention.

### §2.3 The Stitch (the mechanical assembly)

After `Promise.allSettled([lasme, mpse, sro])`, the runner:

```typescript
// THE STITCH — mechanical file assembly, zero LLM tokens
const sectionOrder = ['lasme-section.md', 'mpse-section.md', 'sro-section.md'];
const analysisOrder = ['lasme-analysis.md', 'mpse-analysis.md', 'sro-analysis.md'];

// Stitch doc2 (findings-report.md)
for (const sectionFile of sectionOrder) {
  const sectionPath = path.join(ledgerRoot, sectionFile);
  if (fs.existsSync(sectionPath)) {
    const content = fs.readFileSync(sectionPath, 'utf-8');
    fs.appendFileSync(doc2Path, content + '\n\n');
  }
}

// Stitch doc1 (meta-analysis.md)
for (const analysisFile of analysisOrder) {
  const analysisPath = path.join(ledgerRoot, analysisFile);
  if (fs.existsSync(analysisPath)) {
    const content = fs.readFileSync(analysisPath, 'utf-8');
    fs.appendFileSync(doc1Path, content + '\n\n');
  }
}

// Compute CORRELATIONS from all tags (by this point, ALL tags are in shared.db)
const correlations = computeCorrelationsFromTags(sharedDbPath);
if (correlations) {
  fs.appendFileSync(doc2Path, correlations + '\n\n');
}
```

The stitch is PURE FILE I/O — no LLM calls, no model tokens, deterministic ordering.

### §2.4 The Artifact Ladder Change

Currently: `[PRELIMINARY]` → `[LASME-ADJUDICATED]` → `[MPSE-VERIFIED]` → `[FINAL]`

Concurrent: `[PRELIMINARY]` → `[GATES-RUNNING]` → `[FINAL]`

- `[GATES-RUNNING]` is the new label while all 3 gates are in flight
- `[FINAL]` fires after the stitch completes
- The intermediate labels are removed (they were sequential-only)
- The run-status.json tracks per-gate state: `{gate: 'LASME', phase: 'done'}` etc.

## §3 THE CONCURRENCY SAFEGUARDS (7 surfaces)

### §3.1 doc2 File Contention → Section Files

**Risk:** All 3 gates appending to findings-report.md concurrently = interleaved garbage.
**Safeguard:** Each gate writes its own prefixed section file. The runner appends after allSettled. Zero contention. The existing write_meta_doc append-only enforcement stays (it guards the section files too).

### §3.2 doc1 File Contention → Analysis Files

**Risk:** Same interleaving risk for meta-analysis.md.
**Safeguard:** Same pattern — each meta writes its own prefixed analysis file. The runner appends after allSettled.

### §3.3 Shared Graph → Read-Only + WAL

**Risk:** 14 concurrent hunters querying + tagging the same graph.
**Safeguard:** The graph is READ-ONLY during the audit (extract once, query N times — the existing one-graph law). graph_tag writes go through corbell-bridge → shared.db in SQLite WAL mode. WAL handles concurrent writes (one writer at a time, they queue). The DELETE-before-INSERT by canonical_id makes concurrent tags idempotent — if two hunters tag the same finding, the second write replaces the first (same canonical_id). No duplicates, no corruption.

### §3.4 Ledger Directories → Already Isolated

**Risk:** Hunters writing to shared directories.
**Safeguard:** Already isolated — each hunter has its own subdirectory (R18-lasme-lexicon/, R24-mpse-contract/, etc.). The meta layers each have their own dir too. Zero overlap by construction.

### §3.5 RPM Ledger → Already Designed for Concurrency

**Risk:** 14 concurrent hunters × 2 rounds = 28 simultaneous LLM calls could hit muse rate limits.
**Safeguard:** The RPM ledger's admission + exile mechanism is already designed for concurrent access. When the rate limit is hit, the ledger queues admission (hunters wait). The worst case is slower hunters, not crashes. The muse endpoint handled 6 concurrent fine in prior runs; 14 is the test.

### §3.6 run-status.json → Atomic Writes + Per-Gate State

**Risk:** All 3 gates updating the same status file.
**Safeguard:** The atomic write (tmp+rename) prevents torn reads. Each gate's transition writes its own gate name + phase. The status shows all 3 gates' states concurrently:
```json
{
  "gates": {
    "LASME": {"phase": "done", "huntersFulfilled": 7},
    "MPSE": {"phase": "running", "huntersFulfilled": 2},
    "SRO": {"phase": "running", "huntersFulfilled": 0}
  },
  "overall": "GATES-RUNNING"
}
```

### §3.7 The Artifact Update → Single Writer

**Risk:** Concurrent gates trying to update the artifact file.
**Safeguard:** Only the runner updates the artifact. The gates produce their section files; the runner controls the artifact ladder. Zero concurrent artifact writes.

## §4 THE ENRICHMENT LOSS (the tradeoff, honestly)

**WHAT'S LOST:** The cross-gate enrichment. Currently:
- MPSE's contract hunter reads LASME's lexicon findings → "check the contract at the tower site LASME found"
- SRO's path hunter reads both LASME and MPSE findings → "trace the blast radius from the actor defect"

**WHY IT'S ACCEPTABLE:** The hunters hunt their PREDICATE (the anchor predicate defined in their template). The predicate doesn't change based on prior-gate context — only the FOCUS does. Without the enrichment, hunters scan the full target instead of focusing on prior-findings sites. The findings are the same class, just less narrowly targeted. The operators's ruling: the 3x speedup is worth the focus loss.

**WHAT'S GAINED:**
- 3x speedup (30 min → ~12 min)
- Independent failures (one gate crashing doesn't block the others)
- The CORRELATIONS section is BETTER (computed after ALL tags are in shared.db, not just the prior gates')

**THE V2 OPTION (future):** If the enrichment proves necessary, a future version could:
1. Run LASME first (fastest gate, ~10 min)
2. Then run MPSE + SRO concurrently (both read LASME's output)
3. This halves the time (~20 min) while preserving the LASME→downstream enrichment

## §5 THE IMPLEMENTATION PLAN (file by file)

### §5.1 `src/audit-engine/index.ts` — The Gate Dispatch

**BEFORE (sequential):**
```typescript
// LASME gate
const lasmeMetaResult = await runMetaLayer('LASME', [...lasmeRoster, lasmeMetaTemplate], aetherInputBuilder, aetherLedgerRoot, graphMapper, sharedDbPath, doc1Path, doc2Path);
await updateArtifact(allHydraFindings, lasmeLabel);

// MPSE gate
const mpseMetaResult = await runMetaLayer('MPSE', [...mpseRoster, mpseMetaTemplate], ...);
await updateArtifact(allHydraFindings, mpseLabel);

// SRO gate
const sroMetaResult = await runMetaLayer('SRO', [...sroRoster, sroMetaTemplate], ...);
await updateArtifact(allHydraFindings, finalLabel);
```

**AFTER (concurrent):**
```typescript
// THE CONCURRENT GATES — all 3 fire simultaneously
// Each writes its own section files; the runner stitches after allSettled
const gateResults = await Promise.allSettled([
  runMetaLayer('LASME', [...lasmeRoster, lasmeMetaTemplate], aetherInputBuilder, aetherLedgerRoot, graphMapper, sharedDbPath, lasmeSectionPath, lasmeAnalysisPath),
  runMetaLayer('MPSE', [...mpseRoster, mpseMetaTemplate], aetherInputBuilder, aetherLedgerRoot, graphMapper, sharedDbPath, mpseSectionPath, mpseAnalysisPath),
  runMetaLayer('SRO', [...sroRoster, sroMetaTemplate], aetherInputBuilder, aetherLedgerRoot, graphMapper, sharedDbPath, sroSectionPath, sroAnalysisPath),
]);

// THE STITCH — mechanical file assembly (zero LLM tokens)
stitchConcurrentSections(aetherLedgerRoot, doc1Path, doc2Path);

// Update the artifact to FINAL
await updateArtifact(allHydraFindings, finalLabel);
```

**The run-status transitions:** Add a `[GATES-RUNNING]` write before the Promise.allSettled. Each gate's internal transitions still fire (per-gate start/done). The `[FINAL]` transition fires after the stitch.

### §5.2 `src/hydra/aether-meta.ts` — The Meta Runner

**CHANGE:** The `runMetaLayer` function currently takes `doc1Path` and `doc2Path` and appends directly. Change it to take `sectionPath` and `analysisPath` (the per-gate prefixed files).

The function signature changes from:
```typescript
runMetaLayer(gateName, roster, inputBuilder, ledgerRoot, graphMapper, sharedDbPath, doc1Path, doc2Path)
```
To:
```typescript
runMetaLayer(gateName, roster, inputBuilder, ledgerRoot, graphMapper, sharedDbPath, sectionPath, analysisPath)
```

Internally, the meta agent's doc writes go to the section/analysis files instead of directly to doc1/doc2. The runner-stitch (the mechanical assembly into doc1/doc2) is a NEW function called after allSettled.

### §5.3 NEW: `src/audit-engine/gate-stitch.ts` — The Stitch Function

A new module with the mechanical stitch:
```typescript
export function stitchConcurrentSections(ledgerRoot: string, doc1Path: string, doc2Path: string): void {
  // Section order: LASME → MPSE → SRO (canonical layer order R18→R31)
  const sectionOrder = ['lasme-section.md', 'mpse-section.md', 'sro-section.md'];
  const analysisOrder = ['lasme-analysis.md', 'mpse-analysis.md', 'sro-analysis.md'];

  // Stitch doc2
  for (const f of sectionOrder) {
    const p = path.join(ledgerRoot, f);
    if (fs.existsSync(p)) {
      fs.appendFileSync(doc2Path, fs.readFileSync(p, 'utf-8') + '\n\n');
    }
  }

  // Stitch doc1
  for (const f of analysisOrder) {
    const p = path.join(ledgerRoot, f);
    if (fs.existsSync(p)) {
      fs.appendFileSync(doc1Path, fs.readFileSync(p, 'utf-8') + '\n\n');
    }
  }

  // CORRELATIONS: computed from ALL tags now in shared.db
  // (existing correlation logic, but now it has the full tag set)
}
```

The templates' filterTags definitions stay UNCHANGED — the templates still declare which prior-gate predicates they'd filter on. The runtime behavior changes: at concurrent execution time, the prior-gate output doesn't exist yet, so the filter returns empty. The hunters proceed without the enrichment. No template changes needed.

## §7 THE ANTI-PATTERNS

**AP-C1: THE INTERLEAVED DOC** — Any gate writing directly to doc1/doc2 during concurrent execution. Detection: the stitch function is the ONLY writer to doc1/doc2; any gate-level write to the canonical docs is a violation.

**AP-C2: THE MISSING SECTION** — A gate that fails but its section file is absent from the stitch. Detection: the stitch logs a WARN for each missing section file; the doc2 must contain at least the LASME section.

**AP-C3: THE DUPLICATE STITCH** — The stitch function called twice. Detection: the stitch is idempotent by design (the section files aren't deleted after stitching); the runner calls it exactly once after allSettled.

**AP-C4: THE SEQUENTIAL REGRESSION** — Any `await` between the three gate dispatches. Detection: the three runMetaLayer calls must be inside a single Promise.allSettled array literal — no sequential awaits between them.
